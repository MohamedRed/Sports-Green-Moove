# Notification-Only Retry On A Physical Phone

1 November 2026. Seven independently checked stored-state checkpoints pass
alongside observed parent UI on a provider-reported Pixel 9 Pro, Android 15.
Synthetic accounts and an isolated four-service runtime only. The driver acts
through service calls, not a second phone. No production writes, maps or payments.

The actual Messages screen previously restarted its whole observation when the
notification Retry button was pressed. It now refreshes only the notification
state. Review pages, directory data and confirmed read states are not reset.

Observed sequence: automatic arrival, explicit confirmed read, simulated malformed
alert metadata, error with no stale/false-empty rows, failed retry, restored
metadata and successful explicit retry with the same read state, then another
automatic unread arrival without navigation. Both unrelated callable counters
remain at two throughout error, retry and recovery. All 198 protected records,
original roles, account-disabled states and live trips are unchanged. Two driver
messages create four generic alerts and two pending envelopes; these are not
delivered phone notifications. No team-read receipts are added.

The source-bound isolated build passes 695 JVM cases, including 14 focused cases.
The actual-route instrumented regression compiles but was not executed locally.
Review pagination preservation is JVM coverage, not a physically exercised step.
This simulated authority-read error is not a real radio or network outage.
Installed-APK hashing, whole-head attestation, peer/manager UI, closed-app push,
GPS, iOS and release acceptance remain excluded. The separate earlier failed
capture/full gate is not overridden by this successful phone trial.
