# Invitation Form Reached On A Phone; Signup Still Unconfirmed

One fresh Pixel 9 Pro / Android 15 session on 2 November 2026. The user approved
HTTP `bs-local.com:4185` for this trial only. The page stayed loopback-bound and
the helper retained its exact four SDK ports plus the approved invitation page.
No Force Local, wildcard routing, MITM, request logging, public server, real
account, payment, map request or paid upgrade was used.

The actual Android browser opened the invitation form. A deliberately different
password confirmation produced the expected French rejection. Independent reads
then still showed three original accounts, zero redemption attempts and no child
links or approval requests. An ambiguous one-character correction remained
rejected; the confirmation was then completely re-entered. The next submitted
form showed “L’inscription n’a pas pu être confirmée”. Final independent reads
again found one pending invitation, no redemption attempt, no new account and
no approval request. Do not promote these observations to signup or parent approval.

The native APK was selected from the existing upload. Its local file SHA-256 is
recorded; installed bytes were not independently hashed. Production Android
source is unchanged from the APK's b9a9000 baseline. The browser source was
d55a112; supporting observer/private-input source bytes are separately archived.
The invitation originated in the isolated service fixture, not a newly observed
native share sheet. No native account sign-in or parent-approval step was reached.

Initial remote typing lost punctuation, and the masked local input initially
returned a redacted placeholder rather than a usable fixture password. Those
inputs were cleared before any successful-form submission. The corrected
one-use local input was read through its explicit reveal control, immediately
masked again, closed and never copied to the desktop clipboard. Only the real
fixture value was used for the retained mismatch and unconfirmed submission.
No credential-entry images, invitation fragments or raw network logs are retained.

The three original session-window JPEGs and pixel-exact content-only PNG crops
are retained. All crops were visually reviewed: synthetic email only, passwords
masked, no address bar, provider toolbar, private contact or invitation secret.
These are session captures, not native screenshot exports. No new video exists.

The scoped worker was still running at the post-error check; that is not proof
of uninterrupted routing. A browser networking restriction is a hypothesis, not
an established cause. Chrome documents [secure-context restrictions for local
network access](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access).
The provider documents [its private testing route](https://www.browserstack.com/docs/app-live/local-testing/how-local-testing-works).
Neither document proves the cause of this phone failure. No security permission,
browser protection, proxy target or alternative transport was changed to bypass it.

The provider acknowledged uninstall and returned to Uploaded Apps after Stop
Session. The acknowledgement was observed in the live accessibility output;
the separately saved AX file contains only an unchanged-state delta, not that
message. The operator review records this limitation without replacing the delta.
Independent package absence was not checked. No device administrator,
store-update policy or host-browser permission changed. The host clipboard was
restored. The requested helper shutdown completed with code 130 and its directory
is absent. The owned runtime exited, destroyed its environment, removed both
private fixture files and verified all five service ports closed. Every one-use
private-input listener is closed. The overall release goal remains incomplete.
