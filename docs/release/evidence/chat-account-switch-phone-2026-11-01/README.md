# Pending Chat Privacy Across Account Switching

On 1 November, one physical Pixel 9 Pro (Android 15) retained a parent's
pre-commit pending text while that parent signed out and the driver signed in.
The driver opened the same booking: no messages, no pending text and an empty
composer. After the driver signed out, the parent signed in again and recovered
the pending text/error. One explicit retry produced one confirmed bubble and
emptied the composer. Tapping the pending field before retry did not open the
keyboard; the keyboard opened once the confirmed send unlocked the field.

## Independent Records

Eleven ordered checkpoints retain zero messages/notices through all nine
pre-retry states, then one message and one addressed unread notification after
the parent retries and signs out. Both chat indexes agree. Foreign documents,
claims and live trips remain unchanged. Only the documented parent and driver
profile-initialization timestamps are excluded. The controller prepares the
booking but submits no chat message. Its record checks cannot prove phone UI;
the separately reviewed original session crops provide that observation.

The APK selected in the upload list is `sgm-chat-draft-86746f4.apk`. Its local
original SHA-256 is retained. Six relevant chat/draft sources are byte-identical
to source `86746f4`; the complete current APK and installed remote bytes are not
attested. Backend preparation used `8447897`; observer candidates are bound by
source digests and immutable source archives. No application code changed.

## Limits And Preparation

This accepts only controlled pre-commit pending-text privacy on one Android
phone. It does not independently observe the original pending UUID, exercise
post-commit response loss, prove process restart, peer-phone interaction, real
radio loss, travel/GPS, push delivery, iOS, payment, deployment or release.
The original restart and failed unsent-draft evidence remain unchanged.

Initial parent and driver sign-in attempts showed credential-rejection errors
before successful sign-in. Address/password input was replaced through the
actual Android keyboard; the driver's initial rejection cause was not measured.
The synthetic message was inserted from the keyboard clipboard before sending.
No video was attempted and no browser permissions or browser restart were used.
The private helper needed a separate newline to finish its memory/FIFO handoff;
it did not fail or expose the key. The key was remasked, not rotated or saved.

The separate focused CI job `124696142255` at `8447897` failed waiting for the
cellular network during `network-preparation`, before its outage/send sequence.
Its backend remained reachable on validated Wi-Fi; no default data subscription
or cellular-availability callback appeared. Original instrumentation and JSON,
job metadata, server artifact digest and selected-member provenance are retained.
This phone pass does not override that failure or establish its root cause.
